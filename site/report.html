Web report

How this site got built

What I did, what fought back, and what I would do differently.

Time spent

Around 15 hours in total. Roughly split like this:

Part Hours
Planning, specification and the site map 3
HTML structure and the shared page pattern 3
CSS, layout and responsiveness 4
Media: pictures, audio, video, gallery, map 2
Writing the text, the specification page and this report 2
Validation and fixing what it found 1

The inspiration

I have a friend of mine named Victor who sometimes does funny voice impressions and used to voice act so i chose to make a website for him.

Some parts of the story are true some are not I balanced the story with reality out a little and am pretty satisfied with the final result

The plan

At the beginning i was considering to just do everything with AI, but after it fully implemeted my idea I noticed that, while the final product is very impressive, I wouldnt be learning anything from that. I wanted to somewhat enjoy the learning process myself and started writing by hand.

I have started with the story about the customer. I basically went throgh the course project pdf file from top to bottom and wrote down everything that had to be checked for the story and specification document.

What I learned from past projects is that making a plan and first thinking about the working environment and setting up initial scalable infrastructure is one of the most important things in such project.

This includes several script, namely one serve script used during development and a build/deploy script for deployment.

Structure and the page pattern

I started off by browsing around and looking at popular webpages and see what design patterns they used. One thing i noticed was that most endpoints look very similar to the home page with shared header, footer and even the main content is structured similarly.

Before writing any page I decided on one pattern and stuck to it: a sticky header with the logo and menu, a main area built from stacked sections, and a footer with the links. Each section opens with a small label in the mono font, then a heading, then the content.

Doing it that way was the single best decision in the project. Adding a page became almost mechanical, because the frame was already settled and I only had to think about the content. It also means the site looks like one place rather than seven separate exercises.

The layout is held together by a few small classes instead of many specific ones. A .shell for the page width, a .section for the vertical rhythm, a .panel for anything that looks like a card. Grids and flexbox do most of the work. Floats do one job, the portrait on the About page that the text wraps around.

The hard part: the responsive menu

The solution is a hidden checkbox. In the past i have often been facing problems while coding, back in 2021 I would have to scroll stack overflow for a solution that i can copy and then it would just be trial and error. Nowadays we have AI, but to actually learn yourself from it I have to ask it without it being able to just do all the work itself, like a teacher, not an agent that does all the work on its own. So after a bit of chatting around, i understood the invisible checkbox with the sibling selector

The fun part: CSS animation

The level meter next to the hero on the home page is twenty spans with one keyframe animation on them. The animation has four steps rather than just a start and an end, so the bars do not simply rise and fall, they wobble the way a real meter does.

You can play around a lot with keyframes. After learning about what you can do with them I just played around and went with the vibe and it turned out nicely.

Validation

Every page went through the W3C HTML validator and every stylesheet through the CSS validator. Most of what came back was small and my own fault: a heading left over from testing, a figure caption in a place it is not allowed, an attribute I had written from memory instead of checking.

The validator was more useful than I expected. It does not only find broken HTML, it finds the places where I guessed.

What I would do differently

  • Write the real text earlier. I built the pages with placeholder headings, and placeholders have a way of surviving until the last hour.
  • Split the CSS up from the start. It grew into one long file before I separated the header, footer, animation and page specific parts.
  • Decide the image sizes before exporting anything, instead of exporting twice.

What I learned

Two things stuck. The first is that mobile first is not a style rule, it is the easier direction to work in. Starting narrow and adding space as the screen grows is far less painful than starting wide and taking things away.

The second is how much HTML and CSS can do on their own. There is no JavaScript anywhere on this site. The menu, the animation, the gallery and the form all work without it, which also means they work with scripting switched off.

The course

The parts I enjoyed most were the ones where we were told to go and build something rather than follow along. The animation task was the best of those, because the requirement to use more than just a start and an end frame pushed me into actually understanding keyframes instead of copying an example.

If anything, I would have liked the responsive menu covered in more detail, since it is the one thing everybody needs and the one thing that is genuinely awkward without JavaScript.

Extra points, please

  • No JavaScript at all. The menu is a checkbox, the gallery is an iframe, everything degrades gracefully.
  • The site map is hand-drawn SVG rather than an exported picture, so it scales and its text is selectable.
  • Page specific stylesheets for the booking form, the gallery and these two text pages, loaded after the shared ones.
  • The whole site is reproducible from a Nix flake, with a small build script and a no-cache dev server, so it builds the same way on any machine.
  • The level meter animation, which I am unreasonably pleased with.
